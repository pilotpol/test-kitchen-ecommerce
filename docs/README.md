# Wiki ของโครงการ test-app-

หน้านี้สร้างโดย AI Kitchen จากเอกสารในโฟลเดอร์ `docs/` ทุกไฟล์ผ่านการตรวจความปลอดภัยก่อนนำไปอ่าน

## สรุปข้อมูลนำเข้า

## 1. ภาพรวม

ข้อมูลนำเข้าชุดนี้เป็นของโครงการ test-app ซึ่งเป็นแอป E-commerce ขายเครื่องเขียนให้ลูกค้าองค์กรและโรงเรียน (B2B) สร้างบน Prompt Serve Template ด้วย PromptServe Application Harness ใช้ stack มาตรฐานรหัส `promptserve` และเรียก AI ผ่าน AI Gateway

เป้าหมายของร้านมี 2 ข้อ
- ลดเวลาออกใบเสนอราคา
- ให้ลูกค้าหาข้อมูลสินค้าได้เองผ่านแชตบอต

กระบวนการในแอปเริ่มที่คำขอใบเสนอราคา และจบที่คำสั่งซื้อสถานะ "ยืนยันแล้ว" การชำระเงินและการจัดส่งทำนอกแอป

ที่มาของข้อมูลมี 3 ส่วน
- Briefly_requirement.md ซึ่งมีผลการซักถามรอบก่อน 9 ข้อ
- `docs/ข้อมูลเพิ่มเติมจากแชต.md` ซึ่งเป็นข้อความล่าสุดจากผู้ใช้ มี 2 รายการ
- เอกสารในโฟลเดอร์ `docs/` อีก 3 ฉบับ ซึ่งเป็นแม่แบบและคู่มือทั่วไปที่ไม่มีความต้องการของโครงการ

### สิ่งที่เปลี่ยนจากเดิมตามข้อมูลล่าสุด

ข้อมูลล่าสุดในเอกสาร ข้อมูลเพิ่มเติมจากแชต.md มี 2 รายการ รายการล่าสุดมีผลเหนือรายการก่อน

- รายการ 2026-11-25 16:32 ข้อความ "พอแล้วให้ผ่าน" สรุปฉบับก่อนตีความว่าให้หยุดถามและเดินต่อด้วยสมมติฐาน
- รายการ 2026-11-25 17:17 (แท็บ Spec) ข้อความ "ตามเกณฑ์ ก่อนส่งงานให้ทีมถัดไป ปัญหา หมวดที่ยังไม่ชัดเจน 5. Agent คลังความรู้ และการเชื่อมต่อ, 7. เกณฑ์ยอมรับ, 8. การนำขึ้นใช้งาน" เป็นรายการใหม่ที่สรุปฉบับก่อนไม่มี

ผลของรายการ 17:17 ที่เปลี่ยนจากสรุปฉบับก่อน
- สรุปฉบับก่อนถือว่าไม่มีประเด็นค้างที่ต้องปิดก่อนส่งงาน ฉบับนี้ถือว่ายังมี 3 หมวดที่ผู้ใช้ระบุว่าไม่ชัดเจน ได้แก่ Agent คลังความรู้และการเชื่อมต่อ เกณฑ์ยอมรับ และการนำขึ้นใช้งาน
- ทั้ง 3 หมวดต้องเขียนใน Spec และ Plan ให้ชัดก่อนส่งงานต่อ โดยใช้สมมติฐานที่ตรวจได้ในหัวข้อ 5 และใส่ไว้ในหัวข้อคำถามที่ต้องยืนยัน
- รายการ 17:17 ไม่ได้ให้คำตอบเนื้อหาใด จึงไม่เปลี่ยนความต้องการข้อใด
- ข้อความไม่ได้ระบุว่าหมวดใดไม่ชัดเรื่องอะไร ผมจับคู่กับประเด็นในหัวข้อ 4 ตามที่เห็นว่าใกล้ที่สุด ถ้าไม่ตรงที่ตั้งใจ ขอให้แก้ไข
- ข้อความ "พอแล้วให้ผ่าน" ยังคลุมเครือว่าผ่านเรื่องใด และเขียนไว้ในแท็บผู้ตรวจอิสระ ผมยังถือว่าไม่ต้องการให้ถามซ้ำเป็นรอบใหม่ แต่ไม่ถือว่าประเด็น 3 หมวดข้างต้นปิดแล้ว

## 2. สรุปรายเอกสาร

### 2.1 Briefly_requirement.md (ความต้องการตั้งต้นที่ผู้ใช้พิมพ์)
- ชนิด: บันทึกความต้องการและผลซักถามรอบก่อน (Wayfinder และ Grill-me)
- ประเด็นสำคัญ
  - ผู้ใช้มี 2 บทบาท คือผู้สั่งซื้อขององค์กรและเจ้าหน้าที่ร้าน
  - ผู้สั่งซื้อส่งคำขอและยืนยันใบเสนอราคาเองได้ ไม่ต้องมีผู้อนุมัติภายในองค์กร
  - เจ้าหน้าที่ตั้งราคาโดยยึดราคาตามสัญญาของแต่ละองค์กร แล้วออกใบเสนอราคา
  - เจ้าหน้าที่ใส่และแก้ไขข้อมูลสินค้า สต็อก และราคาตามสัญญาในแอปโดยตรง ไม่มีการนำเข้าจากระบบเดิม
  - Agent แชตบอตแนะนำสินค้าจากแคตตาล็อกและต้องอ้างสินค้าที่มีจริง Agent ไม่ตั้งราคาและไม่ออกใบเสนอราคา
  - มีสมมติฐานรอยืนยัน 7 ข้อ และเรื่องที่รอคำตอบ 3 เรื่อง (บทบาทและสิทธิ์ ข้อมูลส่วนบุคคลและ PDPA บริการอีเมล)
- ข้อมูลและตัวเลขสำคัญ
  - ตัวชี้วัดความสำเร็จ: ออกใบเสนอราคาภายใน 1 วันทำการ วัดจากเวลาส่งคำขอถึงเวลาออกใบเสนอราคา
  - ไม่พบค่าฐานก่อนใช้แอป และไม่พบเป้าหมายอัตราความถูกต้องของแชตบอต
- ข้อสังเกต
  - คำถามข้อ 6 ถามถึง "ส่งคำสั่งซื้อ" แต่ขั้นตอนจริงคือ "ส่งคำขอใบเสนอราคา" แล้วจึง "ยืนยันใบเสนอราคา"
  - เอกสารอ้างถึง Intake_draft.md และ .harness/promptserve/intake.md แต่ไม่ได้ให้เนื้อหามาในคำขอนี้ ผมไม่ได้เปิดอ่าน
  - บันทึกผลค้น Knowledge Base ในเอกสารระบุว่าค้นไม่สำเร็จทุกหัวข้อ เพราะอยู่ในโหมดวางแผน

## 4. ข้อมูลที่ขัดแย้งกันหรือยังไม่ชัด

1. **ข้อความสองรายการล่าสุดในแชตดึงไปคนละทางเล็กน้อย** (ข้อมูลเพิ่มเติมจากแชต.md) รายการ 16:32 "พอแล้วให้ผ่าน" อาจหมายถึงหยุดถามหรือผ่านผลตรวจของผู้ตรวจอิสระ ส่วนรายการ 17:17 ระบุว่ายังมี 3 หมวดไม่ชัดเจน ผมถือว่าไม่ถามซ้ำเป็นรอบใหม่ แต่ต้องเติม 3 หมวดนั้นด้วยสมมติฐานที่ตรวจได้
2. **รายการ 17:17 ไม่ระบุว่าแต่ละหมวดไม่ชัดเรื่องใด** ผมจับคู่ดังนี้ หมวด 5 กับข้อ 5 และ 6 ด้านล่าง หมวด 7 กับข้อ 7 และ 8 ด้านล่าง หมวด 8 กับข้อ 11 ด้านล่าง
3. **ไม่มีคำตอบเรื่องบทบาทผู้ใช้ใน PromptServe และการแยกสิทธิ์ฝั่งเจ้าหน้าที่** (Briefly_requirement.md ระบุว่ารอคำตอบ) ซึ่งเป็นรายการบังคับใน checklist ของแผน
4. **ไม่มีคำตอบเรื่องข้อมูลส่วนบุคคลและ PDPA** ไม่ทราบว่าเก็บชื่อ อีเมล เบอร์โทร ที่อยู่หรือไม่ และเก็บเพราะเหตุใด
5. **บริการอีเมลยังไม่ชัด** ไม่ทราบว่าใช้บริการของแพลตฟอร์มหรือบริการภายนอก และไม่ทราบว่าต้องมีอีเมลแจ้งเตือนหรือไม่ คำเชิญทางอีเมลเป็นทางเดียวที่ผู้สั่งซื้อได้บัญชี จึงมีผลต่อ REQ-06 (เกี่ยวกับหมวด 5 การเชื่อมต่อ)
6. **ไม่ทราบว่า Agent อ่านแคตตาล็อกอย่างไร** อ่านจากฐานข้อมูลของแอปโดยตรง หรือซิงก์เข้าคลังความรู้ใน `knowledge/` (เกี่ยวกับหมวด 5)
7. **เกณฑ์ยอมรับของส่วน AI ยังไม่มี** ไม่มีเกณฑ์ความมั่นใจที่ส่งต่อให้คน ไม่มีเป้าหมายความถูกต้องของแชตบอต และไม่มีกรณีที่ต้องปฏิเสธหรือส่งต่อ นอกจากห้ามตั้งราคาและห้ามแนะนำสินค้าที่ไม่มี (เกี่ยวกับหมวด 7)
8. **ตัวชี้วัดมีเพียงเวลาออกใบเสนอราคา** ไม่มีค่าฐานปัจจุบัน ไม่มีตัวอย่างจริงสำหรับชุดประเมิน และไม่ทราบขนาดงาน (จำนวนสินค้า องค์กร ผู้สั่งซื้อ คำขอต่อวัน) (เกี่ยวกับหมวด 7)
9. **ถ้อยคำคำสั่งซื้อกับคำขอใบเสนอราคาไม่ตรงกัน** คำถามข้อ 6 พูดถึง "ส่งคำสั่งซื้อ" แต่ขั้นตอนจริงคือส่งคำขอแล้วยืนยันใบเสนอราคา ต้องยืนยันว่าไม่มีขั้นอนุมัติภายในทั้งสองจุด
10. **ไม่ทราบวิธีกำหนดราคาตามสัญญา** ราคาตายตัวต่อสินค้า ส่วนลดเปอร์เซ็นต์ หรือตามขั้นปริมาณ และสินค้าที่ไม่มีราคาตามสัญญาแสดงอย่างไร
11. **ข้อมูลการนำขึ้นใช้งานมีน้อย** มีเพียง runbook ที่ระบุการตรวจสุขภาพและการย้อนกลับ ไม่มีข้อมูลบัญชีเริ่มต้น ผู้รับผิดชอบ หรือเกณฑ์ผ่านก่อนนำขึ้นใช้งาน และ runbook ครอบคลุมเหตุขัดข้องเพียง 1 กรณี (เกี่ยวกับหมวด 8)
12. **Intake_draft.md และ .harness/promptserve/intake.md ไม่อยู่ในข้อมูลนำเข้า** จึงไม่ทราบว่ามีข้อมูลขัดหรือเพิ่มหรือไม่
13. **ยังค้น Knowledge Base ไม่ได้** เรียก search_knowledge_base กับ harness-promptserve-app และ promptserve-platform ถูกปฏิเสธอัตโนมัติ เพราะเซสชันอยู่ในโหมดวางแผนและไม่มีช่องทางอนุมัติ ผมไม่ได้ค้นซ้ำ ผลคือยังไม่มีข้อมูลมาตรฐานเรื่องบทบาทผู้ใช้ การเชิญผู้ใช้ภายนอก การผูก Agent กับแคตตาล็อก และบริการอีเมลของแพลตฟอร์ม ทั้ง 4 เรื่องเป็นสมมติฐานจนกว่าจะค้นได้

## 5. คำถามที่ควรถามผู้ใช้ต่อ

ผู้ใช้แจ้งว่า "พอแล้ว" จึงไม่ควรถามซ้ำเป็นรอบใหม่ ทุกข้อด้านล่างเป็นสมมติฐานที่ตรวจได้ซึ่งใช้เขียน Spec ต่อได้ทันที และจะอยู่ในหัวข้อคำถามที่ต้องยืนยันของแผน ข้อ 1 ถึง 3 เป็นหมวดที่ผู้ใช้ระบุว่ายังไม่ชัดในรายการ 17:17 ผู้ใช้แก้ได้เมื่อต้องการ

1. Agent อ่านแคตตาล็อกอย่างไร และอ้างแหล่งอย่างไร (หมวด 5)
   ข้อเสนอ: ให้ Agent เรียกเครื่องมือ (MCP) ค้นสินค้าจากฐานข้อมูลของแอปตามองค์กรของผู้ถาม ตอบด้วยรหัสและชื่อสินค้าจริงทุกครั้ง ไม่ซิงก์เข้า `knowledge/` สำหรับข้อมูลสินค้า ใช้ `knowledge/` เฉพาะเอกสารนโยบายและคำถามที่พบบ่อย ปรับตามผลค้นคลังเมื่อค้นได้
2. บริการอีเมลเชิญและอีเมลแจ้งเตือนใช้ของแพลตฟอร์มหรือบริการภายนอก (หมวด 5)
   ข้อเสนอ: ใช้บริการอีเมลของแพลตฟอร์มถ้ามี และส่ง 3 แบบ คือเชิญผู้สั่งซื้อ แจ้งเมื่อออกใบเสนอราคา และแจ้งเจ้าหน้าที่เมื่อมีคำขอใหม่ ถ้าแพลตฟอร์มไม่มี ให้เหลือเฉพาะอีเมลเชิญ และให้ลูกค้าดูสถานะในแอปแทน
3. แชตบอตต้องปฏิเสธหรือส่งต่อเจ้าหน้าที่เมื่อใด และเกณฑ์ยอมรับของส่วน AI คืออะไร (หมวด 7)
   ข้อเสนอ: ปฏิเสธเมื่อถูกขอให้ตั้งราคา ลดราคา หรือออกใบเสนอราคา และเมื่อถามราคาขององค์กรอื่น ส่งต่อเมื่อถามสินค้าที่ไม่มีในแคตตาล็อก โดยตอบว่าไม่พบและแนะนำให้ส่งคำขอหรือติดต่อเจ้าหน้าที่ เกณฑ์ยอมรับเขียนเป็นพฤติกรรมที่ตรวจได้ เช่น ทุกสินค้าที่แนะนำต้องมีรหัสที่มีอยู่จริงในฐานข้อมูล และไม่มีคำตอบที่มีราคาขององค์กรอื่น
4. ขอตัวอย่างคำถามและคำตอบที่ถูกต้องสำหรับชุดประเมิน AI อย่างน้อย 5 ข้อ เช่น การแนะนำสินค้าตามงบหรือตามจำนวนนักเรียน (หมวด 7)
   ข้อเสนอ: ถ้ายังไม่มีตัวอย่าง ร่าง 10 กรณีใน `evals/` ให้ผู้ใช้ตรวจ ครอบคลุมกรณีปกติ กรณีขอบ และกรณีที่ต้องปฏิเสธ
5. ขนาดงานโดยประมาณเป็นเท่าใด และปัจจุบันออกใบเสนอราคาใช้เวลาเท่าใด (หมวด 7)
   ข้อเสนอ: ตั้งสมมติฐานว่าสินค้าไม่เกิน 2,000 รายการ องค์กรไม่เกิน 100 ราย คำขอไม่เกิน 50 รายการต่อวัน แล้วขอค่าจริงภายหลัง และวัดเวลาออกใบเสนอราคาของแอปเป็นค่าฐานของแอปเอง
6. การนำขึ้นใช้งานเป็นอย่างไร (หมวด 8)
   ข้อเสนอ: ระบบนำขึ้นเองเมื่อทุก backlog รวมเข้างานหลักแล้ว ลำดับ Local Run, Playground และ Go live ใช้บัญชีทดสอบของเจ้าหน้าที่และผู้สั่งซื้อตรวจก่อน Go live และเพิ่มกรณีขัดข้องใน runbook ได้แก่ อีเมลเชิญไม่ถึง และ Agent ตอบสินค้าไม่ตรงแคตตาล็อก
7. ผู้ใช้ฝั่งเจ้าหน้าที่แบ่งสิทธิ์อย่างไร และผู้สั่งซื้อมีสิทธิ์ต่างกันหรือไม่
   ข้อเสนอ: ใช้ 2 บทบาทคือ "เจ้าหน้าที่ร้าน" ทำได้ทุกงานฝั่งร้าน และ "ผู้สั่งซื้อ" เห็นเฉพาะข้อมูลขององค์กรตนเอง ไม่แยกผู้ดูแลสินค้ากับผู้ออกใบเสนอราคาในระยะแรก ส่วนการเปิดแอปผ่านบทบาทของ PromptServe จะยืนยันจากคลังความรู้เมื่อค้นได้
8. แอปเก็บข้อมูลส่วนบุคคลใดบ้าง
   ข้อเสนอ: เก็บชื่อ อีเมล และเบอร์โทรของผู้สั่งซื้อ รวมชื่อและที่อยู่ขององค์กร ไม่เก็บเลขบัตรประชาชนหรือข้อมูลการชำระเงิน ระบุเหตุผลที่เก็บของแต่ละรายการใน Spec เช่น อีเมลใช้เชิญและติดต่อ และให้เจ้าหน้าที่ลบหรือปิดบัญชีผู้สั่งซื้อได้ตามคำขอ
9. ราคาตามสัญญากำหนดอย่างไร
   ข้อเสนอ: เก็บเป็นราคาต่อหน่วยต่อสินค้าต่อองค์กร ถ้าสินค้าใดไม่มีราคาตามสัญญา ให้เจ้าหน้าที่กรอกราคาเองตอนออกใบเสนอราคาและระบบแจ้งเตือนในคิว
10. ใบเสนอราคามีอายุกี่วัน และลูกค้าขอแก้ไขหรือปฏิเสธได้หรือไม่
    ข้อเสนอ: อายุ 30 วัน ปรับค่าได้ ผู้สั่งซื้อกดยืนยัน ปฏิเสธ หรือขอแก้ไขพร้อมหมายเหตุได้ ใบเสนอราคาที่หมดอายุยืนยันไม่ได้
11. ต้องการ PDF ของใบเสนอราคาและคำสั่งซื้อหรือไม่
    ข้อเสนอ: ทำ PDF ทั้ง 2 เอกสาร มีรหัสเอกสาร วันที่ รายการสินค้า ราคา และชื่อองค์กร
12. ระบบต้องตัดสต็อกเมื่อยืนยันคำสั่งซื้อหรือไม่ และแสดงสต็อกให้ลูกค้าเห็นหรือไม่
    ข้อเสนอ: ไม่ตัดอัตโนมัติ เจ้าหน้าที่ปรับสต็อกเอง ลูกค้าเห็นเพียงสถานะ "มีสินค้า" หรือ "หมด" ไม่เห็นจำนวนจริง
13. ขอเนื้อหา Intake_draft.md และ .harness/promptserve/intake.md
    ข้อเสนอ: ถ้าไม่มีข้อมูลเพิ่ม ให้ถือ Briefly_requirement.md เป็นแหล่งเดียวของความต้องการ
14. ต้องการให้ค้นคลังความรู้ (harness-promptserve-app และ promptserve-platform) ก่อนเขียน Spec หรือไม่
    ข้อเสนอ: ค้นหลังออกจากโหมดวางแผน เรื่องบทบาทผู้ใช้ การเชิญผู้ใช้ภายนอก การผูก Agent กับแคตตาล็อก และบริการอีเมล แล้วปรับสมมติฐานข้างต้นตามที่พบ
15. "พอแล้วให้ผ่าน" หมายถึงให้หยุดถามและเดินต่อด้วยสมมติฐานใช่หรือไม่ และรายการ 17:17 หมายถึง 3 หมวดนั้นต้องเขียนให้ชัดใน Spec ก่อนส่งต่อใช่หรือไม่
    ข้อเสนอ: ถือว่าใช่ทั้งสองข้อ และบันทึกทุกข้อในหัวข้อ 5 เป็นสมมติฐานในหัวข้อคำถามที่ต้องยืนยันของ Spec
