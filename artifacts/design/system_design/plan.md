- **ไฟล์ของ harness มีอยู่ใต้รากของแอปแล้ว:** `.promptcoder/skills/promptserv-app-builder/scripts/psapp.mjs`, `.promptcoder/skills/harness-promptserve/references/system-one-two.md`, `.promptcoder/skills/promptserv-app-builder/assets/templates/kb-chat/files/lib/chat-stream.ts`, `.claude/rules/evals.md`, `.claude/commands/review.md`, `.claude/commands/evals.md`, `.claude/commands/golive-check.md` ถ้า backlog ใดเปิดไม่พบไฟล์เหล่านี้ ให้ใช้สาระที่ยกมาไว้ในเอกสารนี้แทน (รูปแบบ SSE ใน Spec หัวข้อ การทำงานของแชต ข้อ 10 และ 11, schema ของ `evals/` ในขั้น 14)
- **โฟลเดอร์ที่ยังไม่มีใต้รากของแอป:** `docs/`, `evals/`, `components/` สร้างใหม่ในขั้น 1, 9 และ 14 แม่แบบ ADR และ runbook ที่ผู้ใช้ให้มาอยู่ในโฟลเดอร์ `docs/` ของรากของ repo หลัก ซึ่งอาจไม่อยู่ใน branch ที่นักพัฒนาใช้ แผนนี้จึงระบุหัวข้อและเนื้อหาขั้นต่ำไว้ในขั้น 1 และ 16 โดยไม่ต้องพึ่งไฟล์ต้นทาง
- **wireframe:** อยู่ที่ `artifacts/design/wireframes/` ที่รากของ repo หลัก (`../../artifacts/design/wireframes/` จากรากของแอป) มี `README.md`, `wireframes.json` และ `page-01.svg` ถึง `page-46.svg` ขณะเขียนเอกสารนี้ `git status` แสดงว่า `artifacts/design/` ยังไม่ได้ commit (A-44) ขั้น 0 จึงตรวจว่า commit แล้วก่อนเริ่มขั้น 9
- **สภาพโค้ดเรื่องสิทธิ์:** `backend/internal/store/store.go` สร้างเพียงตาราง `app_meta` และใน `backend/`, `lib/`, `app/` ไม่มี `app_users`, `is_owner`, `app_users_one_owner`, `requireOwner` หรือ `APP_OWNER_USERNAME` สิ่งเหล่านี้มีอยู่เฉพาะในร่างเอกสารฉบับก่อน งานนี้จึงเป็นการตรวจว่าไม่มีใครเพิ่มเข้ามา ไม่ใช่การลบโค้ดเดิม
- **สภาพ proxy และตัวช่วยเรียก backend:** `app/api/backend/[...path]/route.ts` ตั้ง `X-PS-User` จาก `usernameOf(session)` และ `X-PS-Roles` จาก `session.user.roles` อยู่แล้ว และคัดลอก header จากเบราว์เซอร์เฉพาะรายการ `FORWARDED` ส่วน `lib/backend.ts` มี `backendFetch(path, username, init)` ที่ตั้งเฉพาะ `X-PS-User` และปัจจุบันไม่มีผู้เรียก
- **สภาพ backend:** `backend/internal/httpapi/router.go` มี `requireUser`, `CurrentUser` และ `Roles` แล้ว `backend/main.go` ยังไม่มีตัวรัน `jobs` และ `backend/go.mod` มีเพียง `gin` และ `pgx/v5` ส่วน test ที่มีคือ `router_test.go` ซึ่งไม่ใช้ฐานข้อมูล
- ฟังก์ชันของ SDK คือ `createPromptServRoute` จาก `@repo/ai-gateway-sdk/server` ตาม `app/api/chat/route.ts`
- แม่แบบ `kb-chat` ใช้เป็นแบบอ้างอิงของการอ่านคำตอบและแหล่งที่มา ไม่ติดตั้งทั้งชุด
- สิทธิ์ผู้ดูแลมาจากบทบาทของแพลตฟอร์มใน `X-PS-Roles` เทียบกับ `PS_ADMIN_ROLE_NAME` เท่านั้น

### การเตรียมฐานข้อมูลสำหรับ test (ใช้กับขั้น 3, 5, 6, 8, 11, 15)
- สร้างแพ็กเกจ `backend/internal/testdb/` ที่มีฟังก์ชัน `testdb.New(t *testing.T) *pgxpool.Pool`
- ฟังก์ชันนี้อ่าน environment `TEST_DATABASE_URL` ถ้าไม่ได้ตั้งค่า จะเรียก `t.Skip` บนเครื่องนักพัฒนา และเรียก `t.Fatal` เมื่อ `CI=true` (A-46)
- ทุก test สร้าง schema ชั่วคราวชื่อ `t_<เลขสุ่ม 12 หลักฐานสิบหก>` ตั้ง `search_path` ผ่าน `config.ConnConfig.RuntimeParams["search_path"]` แล้วเรียก `store.Migrate` และลงทะเบียน `t.Cleanup` ที่สั่ง `DROP SCHEMA ... CASCADE` test ทุกตัวจึงแยกข้อมูลกันและรันขนานกันได้
- ไม่เพิ่ม dependency เช่น testcontainers นักพัฒนาใช้ PostgreSQL ที่เข้าถึงได้ เช่น ฐานข้อมูลของ Local Run หรือ PostgreSQL ใน container ของเครื่องตนเอง
- logic ที่ไม่ใช้ฐานข้อมูล (`money`, `bizhours`, การคำนวณใน `quote`, `nextRun` ของ `jobs`, การหาสิทธิ์จาก header) เขียนเป็น unit test ที่ไม่เรียก `testdb`
- เงื่อนไขของขั้น 17: รัน `go test ./...` โดยตั้ง `TEST_DATABASE_URL` และต้องไม่มี test ที่ถูกข้าม

### ขอบเขตของรอบแรก
- ทำระยะที่ 1 ทั้งหมด (S1 ถึง S10 และ E1)
- ระยะที่ 2 ทำเพียง guard ที่ลงทะเบียนทุก path ใต้ `/api/buyer/` ให้ตอบ 403 การล็อกสวิตช์ด้วย `BUYER_PORTAL_IMPLEMENTED = false` และคอลัมน์ที่รองรับระยะที่ 2 ไม่สร้างหน้า C1 ถึง C6
- ส่วนของ AC-03 (404 ข้ามองค์กร) และ AC-23 (ตัวเลขฝั่งผู้สั่งซื้อ) ตรวจเมื่อทำระยะที่ 2 ซึ่งเป็นคำขอเปลี่ยนแปลง

2. **Playground (ขั้น 19):** pipeline ของ AI Kitchen นำแอปขึ้นเองเมื่อทุก backlog รวมเข้า `main` แล้ว การนำขึ้นอัตโนมัติจบที่ขั้นนี้ ก่อนเชิญผู้ทดสอบ ผู้ดูแลต้องตั้ง `BACKEND_INTERNAL_KEY` และยืนยันชื่อบทบาทใน `PS_ADMIN_ROLE_NAME` กับแพลตฟอร์ม ซึ่งเป็นการเปลี่ยน environment ที่ต้องกลับมาถามผู้ใช้ ถ้ายังไม่ได้ตั้ง ให้หยุดการทดสอบไว้ก่อน แอปจะทำงานแบบปลอดภัยไว้ก่อนตามหัวข้อ เงื่อนไขก่อนนำขึ้นใช้งานจริง ของ Intent
3. **Go live (ขั้น 20):** ทำหลังเจ้าของร้านหรือผู้ที่ร้านมอบหมายยืนยันผลบน Playground และบันทึกชื่อกับวันที่แล้วเท่านั้น ไม่มีการนำขึ้น Go live อัตโนมัติ

### สมมติฐานของแผน
- P-01 คำว่า "ไม่มีขั้นอนุมัติ" ใช้กับขั้นเก็บความต้องการเท่านั้น คือผู้รับผิดชอบโครงการคนเดียวทำขั้นนี้ได้ครบ ส่วน Go live ต้องรอการยืนยันของร้านบน Playground ตาม `.claude/commands/golive-check.md`
- P-02 ถ้าผลค้น Knowledge Base ในขั้น 0 ข้อ (ก) ถึง (ง) ขัดกับ Spec ตามเงื่อนไขที่ระบุในขั้น 0 ให้หยุดก่อนขั้น 4 แล้วกลับมาถามผู้ใช้
- P-03 ยังไม่ได้รับตัวอย่างจริงสำหรับชุดประเมิน จึงใช้ 16 กรณีที่ทีมร่างไว้ก่อน และปรับเมื่อได้ตัวอย่างจากลูกค้า (A-25)
- P-04 ส่วนของ AC-03 และ AC-23 ที่เกี่ยวกับผู้สั่งซื้อจริงตรวจเมื่อทำระยะที่ 2 และวิธีให้บัญชีผู้สั่งซื้อภายนอกตัดสินตอนเริ่มระยะที่ 2 (A-29)
- P-05 การเพิ่ม Vitest, `@testing-library/react`, `jsdom`, `gopdf` และฟอนต์ Sarabun อยู่ในสิทธิ์ "นักพัฒนาทำได้เอง: เพิ่ม dependency ที่จำเป็น" งานตามรอบและ test ฐานข้อมูลไม่เพิ่ม dependency
- P-06 เป้าหมายร้อยละ 90 และค่าฐานเป็นไปตาม A-30 ซึ่งยังไม่มีตัวเลขก่อนใช้แอป ถ้าร้านให้ค่าจริง ให้แก้ค่าคงที่ `TARGET_PERCENT` จุดเดียวและเขียน ADR ฉบับใหม่แทน 0008 หน้า S7 อ่านค่าเป้าหมายจาก API จึงไม่ต้องแก้หน้าจอ
- P-07 บริการอีเมลของแพลตฟอร์มยังไม่ได้ค้นยืนยัน (A-17) แผนนี้ใช้ข้อความเชิญที่คัดลอกได้ไปก่อน ถ้าแพลตฟอร์มมีบริการอีเมลและร้านต้องการใช้ ให้ปรับขั้น 8 และ 9 เป็นคำขอเปลี่ยนแปลง
- P-08 ถ้า `PS_ADMIN_ROLE_NAME` ที่แพลตฟอร์มใช้จริงต่างจากค่าเริ่มต้น `Admin` ให้ตั้งค่า environment ให้ตรง โดยไม่ต้องแก้โค้ด
- P-09 สมมติฐานของ Spec ที่ยังรอยืนยัน (A-03, A-04, A-07, A-08, A-09, A-10, A-12, A-18, A-22, A-23, A-27, A-30, A-31, A-32, A-34, A-40 ถึง A-46) แผนนี้ทำตามค่าที่ Spec ระบุไปก่อนและไม่ถือเป็นการยืนยัน ถ้าลูกค้าตอบต่างออกไป ให้แก้ตามจุดที่ขั้นนั้นอ้างไว้
- P-10 wireframe หน้า 8 ถึง 46 ยังไม่ได้ตรวจเทียบกับ Spec (A-36) ขั้น 9 จับคู่ก่อนสร้างหน้าจอ และขั้น 17 ตรวจผล ถ้าพบความขัด ให้แก้ Spec หรือ wireframe ตามที่ผู้ใช้เลือกก่อนส่งขึ้น Playground
- P-11 รอบนี้ค้น Knowledge Base ไม่ได้ เพราะเซสชันอยู่ในโหมดวางแผน จึงถือผลค้นเป็นสมมติฐานเดิมตาม P-02 และงานค้นอยู่ที่ขั้น 0
- P-12 การเปลี่ยนจากเจ้าของแอปเป็นบทบาทผู้ดูแลของแพลตฟอร์มทำให้ไม่มีขั้นสร้างเจ้าของและไม่มี environment `APP_OWNER_USERNAME` ผู้ดูแลคนแรกที่เข้าแอปเพิ่มเจ้าหน้าที่ใน S5 ได้ทันที ถ้าแพลตฟอร์มไม่ส่งบทบาทผู้ดูแลมาใน `session.user.roles` ให้ใช้ P-02
- P-13 Design ล่าสุดมี wireframe 46 หน้า (ฉบับเดิมมี 38 หน้า) แผนนี้สมมติว่า 8 หน้าที่เพิ่มเป็นสถานะหรือหน้าย่อยของรหัสหน้าจอเดิม และไม่ทำให้จำนวนขั้นหรือ endpoint เปลี่ยน ขั้น 9 ระบุว่า 8 หน้านั้นคือหน้าใดใน `docs/wireframe-map.md` (A-39)
- P-14 ถ้า wireframe ยังไม่ถูก commit เข้า `main` เมื่อเริ่มขั้น 9 (A-44) ขั้น 9 และ 17 ใช้กติกาสำรองของ AC-37 และบันทึกแหล่งที่ใช้เทียบในผลเทียบ
