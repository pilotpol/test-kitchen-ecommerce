# เจตนา (Intent)

### ปัญหา
ร้านเครื่องเขียนขายให้องค์กรและโรงเรียน (B2B) ที่สั่งครั้งละมาก และแต่ละองค์กรมีราคาตามสัญญาของตนเอง ร้านยังไม่มีระบบรับคำขอใบเสนอราคา เจ้าหน้าที่จึงใช้เวลาออกใบเสนอราคานาน และลูกค้าต้องถามข้อมูลสินค้าจากเจ้าหน้าที่ทุกครั้ง (ที่มา: `Briefly_requirement.md` หัวข้อ ปัญหาและเป้าหมาย)

### ผู้ใช้หลัก
| ผู้ใช้ | ระยะที่ใช้งาน | บทบาทใน PromptServe | บทบาทในแอป | ความคุ้นเคยกับระบบ |
|---|---|---|---|---|
| เจ้าหน้าที่ร้าน | ระยะที่ 1 และ 2 | ผู้ใช้ที่ลงชื่อเข้าใช้ บทบาท `User` | เจ้าหน้าที่ (`app_users.role = staff`) ทุกคนมีสิทธิ์เท่ากัน (A-18) หน้าจอไม่แสดงป้ายบทบาทข้างชื่อ | คุ้นเคยกับงานขายและใบเสนอราคา |
| ผู้ดูแลระบบ PromptServe | ระยะที่ 1 และ 2 | บทบาทผู้ดูแลของแพลตฟอร์ม (ชื่อบทบาทอ่านจาก `PS_ADMIN_ROLE_NAME` ค่าเริ่มต้น `Admin`) | มีสิทธิ์เท่าเจ้าหน้าที่โดยไม่ต้องมีแถวใน `app_users` และเป็นผู้เดียวที่เปลี่ยนสวิตช์ระยะที่ 2 ได้ แอปไม่มีเจ้าของแอป (A-24) หน้าจอแสดงป้าย "(ผู้ดูแลระบบ)" ข้างชื่อ เป็นผู้ตั้ง environment ของ Playground และ Production | คุ้นเคยกับแพลตฟอร์ม |
| ผู้สั่งซื้อขององค์กร (ลูกค้าภายนอก) | ระยะที่ 2 เท่านั้น ในระยะที่ 1 ติดต่อร้านนอกแอป | ผู้ใช้ที่ลงชื่อเข้าใช้ บทบาท `User` (A-29) | ผู้สั่งซื้อ ผูกกับผู้ติดต่อ 1 คนขององค์กร 1 แห่ง | ผู้ใช้ทั่วไป ไม่ใช่นักพัฒนา |
| เจ้าของร้านหรือผู้ที่ร้านมอบหมาย | ก่อน Go live | ผู้ใช้ที่ได้รับเชิญเข้า Playground | ทดลองในฐานะเจ้าหน้าที่ ยืนยันผลบน Playground และบันทึกใน `docs/golive-checklist.md` ก่อน Go live (A-23) บทบาทนี้เป็นของฝั่งร้าน ไม่ใช่เจ้าของแอปในระบบ | คุ้นเคยกับงานของร้าน |

ผู้รับผิดชอบโครงการใน AI Kitchen ไม่ใช่ผู้ใช้ของแอป แต่เป็นผู้กด Go live หลังร้านยืนยันผลแล้ว (A-52)

### การแบ่งระยะและขอบเขตของรอบแรก
- **ระยะที่ 1 (รอบแรกที่พัฒนา):** ผู้ใช้แอปมีเฉพาะเจ้าหน้าที่และผู้ดูแลระบบ PromptServe ลูกค้าแจ้งคำขอและตอบใบเสนอราคาทางโทรศัพท์ อีเมล หรือช่องทางอื่นนอกแอป แล้วเจ้าหน้าที่บันทึกแทนในแอป แชตผู้ช่วยใช้ได้เฉพาะฝั่งร้าน รอบแรกทำหน้าจอฝั่งเจ้าหน้าที่ครบ (S1 ถึง S10 และ E1) ตาม wireframe ที่จัดทำในแท็บ Design (ฉบับล่าสุดมี 46 หน้า ฉบับก่อนมี 38 หน้า) wireframe อยู่ที่ `artifacts/design/wireframes/` ที่รากของ repo หลัก (A-44) หน้าจอของผู้สั่งซื้อใน wireframe เป็นแบบอ้างอิงของระยะที่ 2 และไม่นับเป็นงานของรอบแรก
- **ระยะที่ 2 (คำขอเปลี่ยนแปลงภายหลัง):** ผู้สั่งซื้อเข้าใช้เอง ส่งคำขอ ตอบใบเสนอราคา และใช้แชตบอตเอง ข้อมูลและ API ออกแบบรองรับไว้ตั้งแต่ระยะที่ 1
- **สิ่งที่ทำเกี่ยวกับระยะที่ 2 ในรอบแรก:** ลงทะเบียนทุก path ใต้ `/api/buyer/` ให้ตอบ 403 และล็อกสวิตช์ `buyer_portal_enabled` ด้วย `BUYER_PORTAL_IMPLEMENTED = false` ผู้ดูแลระบบจึงเปิดระยะที่ 2 ไม่ได้จนกว่าจะมีส่วนผู้สั่งซื้อในรุ่นถัดไป (A-27)
- **เหตุที่แบ่งระยะ:** แอปไม่ส่งอีเมล และยังไม่ได้ยืนยันวิธีให้ผู้ใช้ภายนอกได้บัญชี PromptServe (A-17, A-29)

### เป้าหมาย
1. ลดเวลาตั้งแต่ร้านได้รับคำขอจนเจ้าหน้าที่ออกใบเสนอราคา
2. ให้ข้อมูลและคำแนะนำสินค้าได้เร็ว โดยแชตอ้างเฉพาะสินค้าที่มีจริงในแคตตาล็อก ในระยะที่ 1 เจ้าหน้าที่ใช้แชตตอบลูกค้า ในระยะที่ 2 ลูกค้าใช้แชตเอง

### ผลลัพธ์ที่ต้องได้
ระยะที่ 1
- เจ้าหน้าที่บันทึกคำขอแทนลูกค้าจากแคตตาล็อกที่แสดงราคาตามสัญญาขององค์กรที่เลือก เห็นคิวพร้อมเวลาที่รอและป้ายเกินกำหนด ออกใบเสนอราคาจากร่างที่ระบบเติมราคาตามสัญญาไว้ แล้วบันทึกคำตอบของลูกค้า (ยืนยัน ปฏิเสธ หรือขอแก้ไข) พร้อมช่องทางและหมายเหตุหลักฐาน จนได้คำสั่งซื้อสถานะ "ยืนยันแล้ว" และดาวน์โหลด PDF ของใบเสนอราคาและคำสั่งซื้อได้
- เจ้าหน้าที่ยกเลิกคำขอตามคำขอของลูกค้าได้ขณะคำขอยังรอเสนอราคา ทั้งกรณีที่ยังไม่มีใบเสนอราคาและกรณีที่ลูกค้าขอแก้ไขแล้ว (A-43)
- เจ้าหน้าที่จัดการสินค้า สต็อก องค์กร ราคาตามสัญญา ผู้ติดต่อ และบัญชีเจ้าหน้าที่ได้ในแอป การยืนยันคำสั่งซื้อไม่ตัดสต็อกอัตโนมัติ
- เจ้าหน้าที่สร้างข้อความเชิญผู้สั่งซื้อที่คัดลอกได้ และลบข้อมูลส่วนบุคคลของผู้ติดต่อตามคำขอได้ในหน้าองค์กรและผู้ติดต่อ
- แชตผู้ช่วยตอบคำถามสินค้าและแนะนำสินค้าพร้อมรหัสสินค้าจริง ปฏิเสธงานตั้งราคา ลดราคา และออกใบเสนอราคา และส่งคำถามที่ตอบไม่ได้เข้าคิวของเจ้าหน้าที่
- ผู้ดูแลระบบ PromptServe เป็นผู้เดียวที่เปลี่ยนสวิตช์ระยะที่ 2 ได้ และในรอบแรกตั้งเป็น `true` ไม่ได้ ผู้ดูแลคนแรกที่เข้าแอปเพิ่มเจ้าหน้าที่คนอื่นได้ทันที โดยไม่มีขั้นสร้างเจ้าของแอป
- ทุกหน้าจอฝั่งเจ้าหน้าที่แสดงตัวเลขแจ้งเตือนที่เมนู และแสดงป้าย "(ผู้ดูแลระบบ)" ข้างชื่อเมื่อผู้ใช้เป็นผู้ดูแลระบบ เจ้าหน้าที่ไม่มีป้าย

ระยะที่ 2
- ผู้สั่งซื้อส่งคำขอ ตอบใบเสนอราคา ดูประวัติคำสั่งซื้อ และใช้แชตบอตได้เอง โดยเห็นเฉพาะข้อมูลขององค์กรตนเอง

### เงื่อนไขก่อนนำขึ้นใช้งานจริง
- ลำดับการนำขึ้นคือ Local Run, Playground และ Go live สภาพแวดล้อม ผู้ทดสอบ ข้อมูล และ environment ของแต่ละขั้นเป็นไปตามหัวข้อ สภาพแวดล้อมและการนำขึ้นใช้งาน ของ Spec
- **การนำขึ้นอัตโนมัติครอบคลุมเฉพาะ Playground:** pipeline ของ AI Kitchen นำแอปขึ้น Playground เองเมื่อทุก backlog รวมเข้า `main` แล้ว การนำขึ้นอัตโนมัตินี้ไม่รวม Go live เพราะ Go live ต้องรอการยืนยันของร้าน และ agent ห้ามกด Go live เอง
- **เงื่อนไขก่อนใช้ Playground ทดสอบ:** ผู้ดูแลระบบตั้ง `BACKEND_INTERNAL_KEY`, `SEED_DEMO_DATA=true` และยืนยันชื่อบทบาทผู้ดูแลใน `PS_ADMIN_ROLE_NAME` กับแพลตฟอร์ม รวมทั้งยืนยันว่าบัญชีผู้ดูแลเปิดแอปภายใต้ `roles: ["User"]` ได้ (A-24, A-35) การนำขึ้นอัตโนมัติไม่ได้รอเงื่อนไขนี้ ถ้ายังไม่ได้ตั้งค่า แอปบน Playground จะทำงานแบบปลอดภัยไว้ก่อน คือ route `/internal/` ตอบ 403 ทำให้แชตไม่พร้อมใช้งาน และใช้ชื่อบทบาทค่าเริ่มต้น `Admin` ขั้น 19 จะหยุดการเชิญผู้ทดสอบและการรันชุดประเมินไว้จนกว่าผู้ดูแลจะตั้งค่าครบ การตั้ง environment เป็นการเปลี่ยนสภาพแวดล้อม จึงต้องกลับมาถามผู้ใช้ก่อน แอปไม่ใช้ `APP_OWNER_USERNAME`
- ก่อน Go live ชุดประเมิน AI ใน `evals/` (16 กรณีที่ใช้ข้อมูลทดสอบที่ระบุค่าไว้ใน Spec) ต้องผ่านตามเกณฑ์ AC-27 และแชตต้องตอบภายใน 10 วินาทีทุกกรณี
- เจ้าของร้านหรือผู้ที่ร้านมอบหมายต้องยืนยันผลบน Playground และบันทึกชื่อกับวันที่ก่อน Go live จากนั้นผู้รับผิดชอบโครงการเป็นผู้กด Go live (A-52)
- Production เริ่มจากฐานข้อมูลที่ไม่มีข้อมูลทดสอบ และไม่ตั้ง `SEED_DEMO_DATA` (A-49)
- การย้อนกลับใช้รุ่นก่อนหน้าจาก Playground ได้เสมอ เพราะ migration ของรอบแรกเป็นแบบเพิ่มอย่างเดียว (AC-39)
- ข้อความ "ไม่มีขั้นอนุมัติ" ใช้กับขั้นเก็บความต้องการเท่านั้น ไม่ใช้กับ Go live
- ก่อนเริ่มพัฒนาส่วนสิทธิ์ ต้องค้น Knowledge Base ของแพลตฟอร์มเพื่อยืนยันชื่อบทบาทผู้ดูแล บริการอีเมล วิธีให้ Agent ได้ข้อมูลแคตตาล็อก และการแยกฐานข้อมูลของ Playground กับ Production (ขั้น 0 ของ Plan) ผลของแต่ละข้อกำหนดไว้ล่วงหน้าในหัวข้อ ผลที่กำหนดไว้ล่วงหน้าของการตรวจขั้น 0 ของ Spec เฉพาะกรณีที่ระบุว่าขัดกับ Spec ให้หยุดและกลับมาถามผู้ใช้
- wireframe หน้า 1 ถึง 7 แสดง "(ผู้ดูแลระบบ)" แล้ว ขั้น 9 ต้องจับคู่ทั้ง 46 หน้ากับรหัสหน้าจอก่อนสร้างหน้าจอ และก่อนปิดงานต้องเทียบหน้าจอที่สร้างกับ wireframe ครบ 46 หน้า โดยเฉพาะหน้า 8 ถึง 46 ซึ่งยังไม่เคยตรวจเทียบกับ Spec (A-36, A-39) และต้องไม่มีหน้าใดแสดง "(เจ้าของแอป)"
